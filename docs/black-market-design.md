## 0. 本轮结论

### 0.1 规则变更

1. **鱼价只看词条**：`渔币 = 词条数 × 1`，不再看鱼种、重量、稀有度。鱼的重量仍然只用于展示。
2. **订单每个玩家独立**：每人每天一张「1 收购词条 + 2 禁用词条」的订单，按已解锁海域生成，可花渔币刷新。
3. **老虎机 → 超级刮刮乐**：投入任意数量、任意种类的未刮开卡；服务端先结算这批卡的实际奖励并按奖励合并成「底池」，据此算出每种奖励的热度；再刮一张 **9 格超级卡（3×3，默认；可配 3–9 格）**，奖池是这批卡奖池的并集，每个奖励图标旁标注热度系数，最终按「底池 × 热度 × 匹配倍率」结算。
4. **入口与模式**：黑市不是左侧导航里的普通页，入口是左上角品牌锁；**解锁海沟**后品牌锁出现紫色斜线循环光效，直到玩家第一次点击。进入后左侧导航整体替换为「收购 / 超级刮刮乐 / 商店」，点品牌锁返回鱼市；黑市模式下不挂载钓鱼等鱼市页面。

### 0.2 可行性判定

**可行。核心是「形状控方差，缩放控期望」：**

- **方差由超级卡的形状决定**：默认 9 格、`baseline=0.05`、`fPower=2`、`fMax=10`、热度 clamp 0.25–4。4 种奖励时 9 个图标通常出现 3–4 连；吃到 4+ 连的奖励可拿到其底池的 **2–3×**，其余未成连的奖励只剩 **1–10%**（示例：鱼币四连 60，木/树脂/晶片合计 0.85）。9 格不是靠「无对」制造方差，而是靠「集中到某一个奖励」。
- **期望由 `payoutRate` 决定**：总期望与 `payoutRate` 成正比，缩放不改变方差。服务端按 `E[B×h]` 和 `E[f]` 反推 `payoutRate`，把长期期望锁在 `targetEv=0.975`，允许区间 `[evMin=0.95, evMax=1.00]`。
- **期望按统一价值算**：鱼币 1、材料按黑市回收价、锁钥按配置；`E/B/P` 都乘 `v_j`，不能把 1 个浮木纤维和 1 个鱼币当同价值。
- **热度会放大幸运底池**：`E[B×h] = E[B] + sensitivity × Var(B)/(E[B]+1)`（`+1` 平滑版），不能拆成 `E[B]×E[h]`。附录 A 的不含 `+1` 理论值下，1 张约 7.8×、10 张约 1.68×、100 张约 1.07×；所以 `payoutRate` 必须按这批投入的 `E/Var` 现算，不能固定 0.95。
- **`E[f]` 不是 1，也不是固定区间**：9 格默认预设下，`E[f_j]` 随 `p_j` 从 ≈`baseline`（0.05，极稀有奖励）到 ≈1.85（p≈0.1–0.25）之间变化；必须按二项分布逐奖励精确算，并进入 `payoutRate` 公式。
- **保守校准**：常规批量下解析式忽略热度 clamp，算出的 `payoutRate` 偏小，实际期望 ≤ 模型值；但小批量/高偏度奖池里线性近似本身会明显低估（1 张卡时解析费率可能只有模拟值的 2/3），必须由 §8.11.7 的 `Var/E²`/clamp 风险 guard 强制走模拟。
- **线上兜底**：每次超级卡记录 `payoutRate`、`ΣE`、实付；按 `(poolHash 组合, 张数档位)` 全局滚动统计 `实付/ΣE`，超出 `[0.95, 1.00]` 时告警并微调 `targetEv`。单次结果可以很大或很小，控制的是长期期望。
- **兼容任意配置**：每张卡带 `pool` 快照，超级卡只认快照；任意槽数、奖池、权重、`need`、同名奖励、发卡后改配置/删卡种都有明确行为（§8.11）。
- 不想维护解析/模拟时，可把 `sensitivity=0`：热度恒 1，`payoutRate≈0.975/E[f]`，仍有 9 格的强方差，只是没有「按实际奖励加热度」的惊喜。

**结论：推荐「底池制 + 9 格高方差形状 + 有界热度 + 运行时解析/模拟校准 + 滚动审计」；可行，且支持任意混合投入与任意可配置刮刮乐。**

### 0.3 上一轮遗留问题，已解决

1. **`payoutRate` 不是概率，不能 clamp 到 1**
   - 现象：稀有奖励的 `E[f_j]` 很小（可低到 `baseline=0.05`），反推的费率可以远大于 1；旧稿写「`>1` clamp 1.0」会直接欠发。
   - 处理：费率只要求有限且落在 `[0.01, 1e6]`；审计看 `实付价值 / Σ(E×v)`，不看费率绝对值。§8.5、§8.8、§13 已统一。
2. **未刮卡面对客户端保密**
   - 现象：底池来自投入卡的实际结算；如果客户端能读到 `card.face`，玩家只挑高产出卡，EV 控制失效。
   - 处理：落库保留 `face`，HTTP 响应层新增 `redactScratchFaces` 剥离 `ready` 卡的 `face`/`payout`；刮开走 `revealScratch` 返回。列为开发第 0 步前置（§13.1、§15）。
3. **未刮卡面保密与「卡种被删」的冲突**
   - 现象：客户端看不到 `face`，卡种又被删时，前端不知道这张卡有几格、该画几个占位。
   - 处理：下发 `slots`（只是格数，不是内容）；`poolHash` 只作标识。渲染不需要知道奖励是什么。

## 1. 目标与非目标

### 目标

1. 给仓库里不想卖商会的鱼一个第二出口；鱼价只看词条，规则一眼能懂。
2. 给溢出的低阶材料一个回收出口。
3. 给未刮开的刮刮乐一个**批量、快速、高方差**的消耗方式，且比一张张刮更有仪式感。
4. 用渔币承载商会/彩票买不到的限定道具与服务。
5. 不改动商会定价、彩票开奖、FX 公式、仓库容量规则。
6. 黑市是「第二模式」：入口是左上角品牌锁，进入后左侧导航整体替换；不做成鱼市导航里的一个普通页。

### 非目标

- 玩家间交易、渔币 ↔ 鱼币兑换。
- 全服共享订单表（v1 用玩家快照；见 §6.2）。
- 新增卡种（v1 复用现有卡池）。
- 黑市鱼影响 FX（用户明确要求，但必须配每日配额，见 §12）。
- 用客户端上报的刮开比例影响任何经济数值。
- 黑市内的钓鱼遥控/停钓开关（想操作钓鱼回鱼市）。
- 黑市模式持久化到 URL 或刷新后保持（v1 刷新回鱼市）。

## 3. 入口与页面

### 3.1 解锁

- 默认 `config.blackMarket.unlockDepth = 'deep'`（**解锁海沟时**开放；`deep` 是海沟，`rift` 是裂谷）。
- 解锁判定：`enabled && unlockedDepths.includes(config.blackMarket.unlockDepth)`。`enabled: false` 时入口不可用，所有黑市动作返回 `BLACK_LOCKED`；已有渔币/购买/订单保留。
- 未解锁时左上角品牌锁保持普通鱼市样式，点击不进入、不报错；解锁后品牌锁出现**紫色斜线循环光效**，直到玩家第一次点击进入。
- 解锁瞬间（`unlockDepth` 动作返回）就应看到光效，不需要重新登录。
- 后台可把 `unlockDepth` 改到更晚的海域（`rift`/`abyss`）或更早（`open`）；非法值回退 `deep`。

| 状态 | 条件 | 品牌锁 | 点击行为 |
| --- | --- | --- | --- |
| 未解锁 | `!enabled` 或未解锁 `unlockDepth` | 普通「深海鱼市」，`disabled` | 无 |
| 已解锁 · 未进入 | 解锁且 `!introSeen` | 「深海鱼市」+ 紫色扫光 | 进入黑市，停光效，发 `blackAcknowledge` |
| 已解锁 · 已进入 | 解锁且 `introSeen` | 「深海鱼市」，无扫光 | 进入黑市 |
| 黑市模式 | `activeTab` 是黑市页 | 「无灯黑市」+ 紫色图标 + 返回箭头 | 回鱼市上次页面 |
| 黑市模式但被禁用 | `activeTab` 是黑市页且 `!enabled` | 只存在一帧；`useEffect` 立即回退 | 自动回鱼市 + toast |

### 3.2 入口与模式切换（左上角品牌锁）

黑市不是左侧导航里的一个普通页面，而是「换一套导航」的第二模式。入口是左上角的品牌锁（图标 + 文字），点击切换：

```jsx
<button className="brand-switch" disabled={!blackUnlocked && !blackMode}
  aria-label={blackMode ? '返回深海鱼市' : blackUnlocked ? '进入无灯黑市' : '深海鱼市'}>
  <span className="brand-mark">{blackMode ? <Skull size={20} /> : <Anchor size={20} strokeWidth={2.2} />}</span>
  <span className="brand-copy"><strong>{blackMode ? '无灯黑市' : '深海鱼市'}</strong></span>
  {blackMode && <ChevronLeft className="brand-back" aria-hidden="true" />}
</button>
```

- **鱼市模式**：品牌锁显示「深海鱼市」+ 锚图标；已解锁且启用时，点击进入黑市。
- **黑市模式**：品牌锁显示「无灯黑市」+ 紫色骷髅图标 + 返回箭头；点击回到鱼市上次所在的页面。
- 品牌锁整体是 `<button>`，图标和文字都可点；不要只给图标绑点击。
- 未解锁/禁用时用 `disabled`（不是 `pointer-events:none`），点击无效且读屏不会误报「可进入」；不弹 lore。
- 键盘：`Enter`/`Space` 可切换；`aria-label` 说明当前动作。
- 移动端：品牌锁在抽屉顶部，点击切换后关闭抽屉；`mobile-close` 仍只负责关抽屉，不触发切换（`stopPropagation`）。
- 模式不持久化：刷新后回到鱼市默认页（`activeTab` 仍是本地 state）；如果希望刷新保持黑市模式，可把 `activeTab` 存 localStorage 或 `settings`，v1 不做。
- **顶栏货币 chip 跟随模式**：鱼市模式显示鱼币（金色），黑市模式显示渔币（紫色，`aria-label="渔币 N"`）。黑市里没有鱼币消费，显示鱼币只会和渔币混淆。

#### 3.2.1 首次进入的紫色斜线光效

- 条件：`enabled && unlockedDepths.includes(config.blackMarket.unlockDepth) && !blackMarket.introSeen && !introAckRef.current && !blackMode`。
  - `introAckRef` 是本次会话的本地标记：点过一次就为 true，不等服务端回包；避免网络慢时扫光在点击后还继续闪。
  - 下次刷新时 `introAckRef` 重置，但服务端 `introSeen` 已为 true，所以不会复现。
- 表现：品牌锁内部一条紫色斜线光带从左到右循环扫过，周期约 2.8s；同时有很淡的紫色描边/外发光。颜色用 `#a06bff`（渔币紫）。
- 只装饰，不改变布局；`pointer-events: none`；不遮挡点击。
- `prefers-reduced-motion: reduce`：关闭扫光动画，改成静态紫色描边 + 一个小紫点；仍然可见，但不闪。
- 玩家第一次点击品牌锁进入黑市时：本地先置 `introAckRef=true`（本会话不再显示扫光），同时发 `blackAcknowledge` 落库；动作失败也不回滚本地，下一次进入黑市时再重试一次，直到服务端 `introSeen=true`。
- 这样断网/超时不会让扫光在本次会话里反复闪；刷新后如果服务端仍未落库，扫光会再出现一次，属于可接受的降级。
- 光效只在鱼市模式出现；进入黑市后不再显示。
- 进度重置后 `introSeen=false`；如果玩家再次解锁海沟，光效会再次出现（视为新进度）。
- 后台 `enabled=false` 时不显示；重新启用且未看过时再显示。
- 移动端抽屉关闭时，左上角汉堡按钮也带一个同色小紫点（或极轻的扫光），提示抽屉里有新入口。

- 扫光带最大不透明度建议 `.38` 左右，避免盖住「深海鱼市」四个字影响可读性；需要更明显就加外发光，不要加高光带透明度。

#### 3.2.2 黑市模式的外观

- 外层 `.app-shell` 加 `data-mode="black"`；只覆盖颜色变量（surface / line / ink / accent），不改布局、不改字号、不改栅格。
- 黑市模式：`--accent: #a06bff`，背景更深一档，卡片边框更冷；鱼市模式完全保持现状。
- 不做全屏转场动画；切换是即时的。最多给 `.main-content` 一个 120ms 的淡入，`prefers-reduced-motion` 下取消。
- 主题「无灯」（`[data-theme="void"]`）是玩家购买的独立主题，和 `data-mode="black"` 正交：黑市模式不强制套用 `void`，避免「进黑市就白送主题」。
- 黑市模式下 `document.title` 可改为「无灯黑市 · 深海鱼市」；不改路由，不写 URL。

```js
const BLACK_NAV = [

  { id: 'black-super', label: '超级刮刮乐', icon: Gift },
```

（`Skull`、`Store`、`ChevronLeft` 在 `lucide-react` 里都有，已确认。）

- `activeTab` 是唯一模式来源：`BLACK_NAV.some((item) => item.id === activeTab)` → 黑市模式；否则鱼市模式。
- 进入黑市默认落到「收购」，或上次停留的黑市页；返回鱼市回到上次的鱼市页。用 `lastFishTabRef` / `lastBlackTabRef` 记录。
- 黑市模式下不渲染钓鱼/彩票/刮刮乐/深海FX/潮汐商会/钓竿与背包/天赋/中奖统计/设置/管理后台；不是 CSS 隐藏，是不挂载。
- **黑市模式下钓鱼仍在服务端继续**：不挂载钓鱼页不等于停钓；`sync` 照常推进，返回鱼市能看到结果。不要在切模式时发 `toggleFishing`。
- 黑市模式下不显示彩票待兑奖角标；管理后台入口也不显示。管理员要进后台，先点品牌锁回鱼市。

## 4. 核心循环

```
鱼（符合当日订单） ──→ 渔币
材料（可回收）     ──→ 渔币
渔币 ──→ 限定钓竿 / 维修 / 刷新 / 配额 / 主题 / 黑市秤

未刮开的卡（任意种类，1–200 张）
      │
      ├─ 服务端结算投入卡 → 实际奖励 B（底池）
      ├─ 按 B 与期望 E 算每种奖励的热度 h
      ├─ 生成 9 格超级卡（3×3 默认；投入卡奖池快照，图标带 h）
      └─ 玩家刮开 → 按「B × h × 匹配倍率 × payoutRate」结算
```

- 黑市本身不印鱼币：超级刮刮乐会把卡池里的鱼币兑现。
- 渔币只来自鱼和材料；超级刮刮乐不是渔币来源。
- 超级刮刮乐是**刮刮乐的批量替代**，不是渔币商店的替代。

## 5. 鱼类估值（只看词条）

### 5.1 公式

```
value = max(1, traits.length × traitBonus)
```

- `traitBonus` 默认 1；后台可调。
- 不看鱼种、不看重量、不看稀有度、不看具体是哪些词条。
- 每日订单只决定**能不能卖**：含指定 1 个词条、且不含指定 2 个词条。
- 因此同样 3 条词条的鱼，不管是河口的银鳞鲹还是深渊的水母，都值 3 渔币。
- 这正好符合「根据鱼的词条数，每个词条给予一个渔币」。

### 5.2 示例

| 鱼 | 词条 | 渔币 |
| --- | ---: | ---: |
| 银鳞鲹 | 1 | 1 |
| 玄甲石斑 | 2 | 2 |
| 星痕旗鱼 | 3 | 3 |
| 静海幽灵水母 | 6 | 6 |

- 有黑市秤（+10%）时：`value = max(1, round(value × 1.1))`。
- 6 词条 + 黑市秤 = 7 渔币。
- 旧鱼、旧存档不需要迁移重量/种类；`fish.weight` 保持现状，仅展示。

### 5.3 影响面

- 商会报价 `fishQuotePrice` 仍然只按词条种类/组合计算，不受黑市影响。
- FX 只认词条，不认鱼价。
- 鱼价只看词条数，`traits` 缺失/空数组时回退为 1，避免旧数据卖 0。

## 6. 每日收购单

### 6.1 规则

每天（与 FX 交易日同一个本地零点）为每个玩家生成一张收购单：

- **收购 1 个词条**（`demand`）；
- **禁用 2 个词条**（`banned`，互不相同，且不等于 demand）；
- 只有「新鲜、含 demand、且不含任何 banned」的鱼可以卖给黑市；
- 每条鱼给 `max(1, 词条数 × traitBonus)`；
- 每日最多收购 `dailyQuota` 条（默认 40，可通过商店扩到 100）。

### 6.2 每个玩家独立

- 全服订单可能点到一个玩家尚未解锁海域的词条（例如只开到港湾却要「棱彩」），当天直接不可玩。
- 每个玩家一张可以按「已解锁海域」生成，保证当天有事可做。
- 刷新服务需要个人订单；全服订单下刷新只能全服重掷，容易变成互相干扰。
- 本作本来就是「共享 FX/彩票 + 个人存档」的结构，个人订单不破坏世界观；叙事上就是「你的线人今天要这批货」。
- 如果以后想要全服订单，可以加 `black_market_orders` 全局表并把刷新改成全服事件；v1 不做。

### 6.3 生成算法

输入：玩家当前 `selectedDepthId`、已解锁海域、`config.depthTraitWeights`、`cryptoRandom`。

1. 可用词条列表 `T`：
   ```
   T = config.traits.filter(t =>
     depthsFor(state).some(d => weight(d, t) > 0)
   )
   ```
   如果 `T` 少于 3 个（配置异常），退化为 `config.traits`。
2. 枚举候选 `(demand, banned1, banned2)`：
   - `demand ∈ T`；
   - `banned1, banned2` 从 `T \ {demand}` 中取，顺序无关，共 `|T| × C(|T|-1, 2)` 个；8 个词条时 168 个。
3. 对每个候选，估算「当前海域一条鱼符合条件」的概率：
   ```
   P(eligible | d) = 1/(kmax-kmin+1) × Σ_k Σ_{S⊆T, |S|=k,
       demand∈S, S∩banned=∅} P_draw(S)
   ```
   `P_draw(S)` 是无放回加权抽取的概率，复用 `traits.js` 里 `subsetDrawChance` 的逻辑（目前是私有函数，需要导出或抽成公共 helper）。
   - `d` 取玩家当前的 `selectedDepthId`（生成时正在钓的海域）。
   - 订单本身**不绑定海域**：生成后换海域，资格仍只按词条判定；换到更浅的海域可能更难凑，玩家可以刷新。
   - 8 个词条、k ≤ 6，枚举量 ≤ 246 个子集/海域，单次生成可忽略。
4. 过滤 `P ∈ [0.12, 0.45]`。在带内按分数加权随机取一个：
   ```
   score = 1 - |P - 0.25| / 0.25
         + 0.15 × (demand 的稀有度)
         + 0.15 × (banned 的常见度)
   ```
   取分数最高的前 8 个候选，按分数加权抽 1 个。
5. 如果带内没有候选，取 `|P - 0.25|` 最小的候选，标记 `forced: true`（仅调试/后台可见）。
6. 记录：
   ```js
   order = { demand, banned: [b1, b2], depthId, acceptance, generatedAt }
   ```
   `depthId` 只记录生成时的海域，供后台/调试；资格判定与海域无关。

> 生成用服务端 `cryptoRandom`。订单在当天首次读取时生成一次并落库；同一玩家同一天不会因为刷新页面而变。

### 6.4 日切与离线

- 日切时刻：`fxDayClose(fxDayIndex(now))`，即服务器本地零点，与 FX 对齐。
- `state.blackMarket.day` 存 `fxDayIndex`；不等于今天就重置：
  - `order = null`（由生成器补）
  - `soldToday = 0`
  - `rerolls = 0`
  - `dailyBuys = {}`
  - 保留：`coins`、`quotaBonus`、一次性购买、累计统计、`lastSuper`、`superDust`
- 离线多天不补订单：回来只看到今天的单；错过的日期不累积配额。
- 日切在服务端 `syncPlayerLocked` 里执行（拿到当前 config 和 `cryptoRandom`），不依赖客户端时间。

### 6.5 资格与出售

```
eligible(fish) =
  fish.status === 'fresh' &&
  fish.traits.includes(order.demand) &&
  fish.traits.every(t => !order.banned.includes(t))
```

- 出售动作只接受 `fishIds`，服务端逐条重新校验（状态、资格、配额），不信任客户端算出的价值。
- 批量出售按客户端传入顺序处理；卖到配额为止，实际成交/跳过/是否触顶写进 `blackMarket.lastSale`。
- 每条鱼：
  - `status: 'fresh' → 'black'`，记录 `blackValue`、`soldAt`；
  - `blackMarket.coins += value`；
  - `soldToday += 1`；
  - `stats.fishSold += 1`、`stats.coinsEarned += value`。
- **不调用 `fxAppendFlow` / `fxExchangeFlow`**（§12）。
- 出售后仓库空出位置；不会自动恢复钓鱼（与商会兑换一致），由玩家自己点继续。

### 6.6 刷新

- 价格 25 渔币，每日 3 次（`config` 可调）。
- 重掷 `demand/banned`，**不重置** `soldToday`、配额、当日购买次数；`rerolls += 1`。
- 收购页刷新与商店里的「刷新收购单」共用同一个每日次数：任一入口刷新都会同时增加 `rerolls` 与 `dailyBuys.refresh`，两个入口看到的是同一个剩余次数。
- 重掷后已经卖掉的鱼不受影响；仓库里原本可卖的鱼可能变得不可卖，这是刷新的风险。
- 前端两段式按钮（第一次点变「确认刷新 25 ◉」，3 秒内再点才发请求），不做浏览器原生 confirm。

## 7. 材料回收

### 7.1 回收表

只回收 5 种可再生的强化材料；**锁钥不回收**（进度钥匙，误卖会卡海域）。

| 材料 | 回收比例 | 单组渔币 |
| --- | --- | ---: |
| 浮木纤维 | 20 → 1 | 1 |
| 潮汐树脂 | 20 → 1 | 1 |
| 深蓝晶片 | 5 → 1 | 1 |
| 渊核碎片 | 2 → 1 | 1 |
| 旧日合金 | 1 → 2 | 2 |

### 7.2 交互

- 玩家按「想换多少渔币」输入：
  ```
  units = clamp(int(requested), 0, floor(holding / per))
  cost  = units × per
  coins = units × coinsPerGroup
  ```
- 服务端校验 `holding >= cost`，扣材料、加渔币。
- 输入框上限 `floor(holding/per)`；`最大` 一键填满。
- 单次上限 1000 组（防御性），超出分次。
- 统计：`stats.materialsSold`、`stats.coinsEarned`。

## 8. 超级刮刮乐

### 8.1 概念

玩家投入 N 张未刮开的卡（种类不限）；服务端先把这 N 张卡结算掉，按奖励合并成**实际总量 B**（底池）。底池不直接发给玩家，而是作为超级卡的「燃料」：

1. 用 B 与这 N 张卡的**期望总量 E** 计算每种奖励的热度 `h`；
2. 用这批卡的**奖池并集**生成一张 **9 格超级卡**（3×3 默认；`slots` 可配 3–9），每个图标旁标注该奖励的 `h`；
3. 玩家刮开超级卡，按 `B × h × 匹配倍率 × payoutRate` 结算。

### 8.2 输入与底池

- 任意种类、`status === 'ready'` 的卡；数量 1–200。
- 每张卡用发卡时已存的 `face` 结算；同时用它的 **`pool` 快照**（slots + 奖池）算期望，不读当前 `config.scratchTypes`（详见 §8.11）。
- 奖励按 `kind:name` 合并（鱼币和材料同名也算不同奖励）：
  ```
  B_j  = Σ_cards 该卡对奖励 j 的实际产出
  E_j  = Σ_cards μ_{card,j}
  Var_j = Σ_cards σ²_{card,j}
  ```
  `μ_{card,j}` / `σ²_{card,j}` 是这张卡按自己的 `pool` 快照对奖励 j 的单卡期望/方差。
- `μ/σ²` 按 `pool` 快照的哈希懒计算并缓存（二项分布精确公式，见 §8.11.2；超大组数才退化为模拟），不在每次请求里现算；新增卡种、改奖池不需要改黑市代码。
- 超级卡的奖池 = 投入卡**可支付奖励**的并集：
  ```
  w_{card,j} = 该卡快照里奖励 j 的权重 / 该卡快照里「进入超级奖池」的奖励总权重
  w_j = Σ_cards w_{card,j}
  p_j = w_j / Σ w = (1/N) × Σ_cards p_{card,j}
  ```
  分母只算 `μ>0 且 v>0` 的奖励；`μ=0`/`v=0` 的死奖励不稀释活奖励。先按卡归一，避免「某卡种权重写成 1000、另一卡种写成 1」时概率被权重尺度绑架；`p_j` 自然等于各卡出现概率的平均（N = 本批卡数，且每张卡至少有一个可支付奖励）。同名奖励只出现一次。
- 投入卡被消耗，底池不直接入账；投入结算只用于算热度和作为超级卡的乘数基数。
- 统计：`stats.superConsumed += N`。

### 8.3 热度

```
ratio_j = (B_j + 1) / (E_j + 1)
h_j = clamp(1 + sensitivity × (ratio_j - 1), hMin, hMax)
```

- 默认 `sensitivity = 1.2`，`hMin = 0.25`，`hMax = 4`；三个值都可在后台调。
- `+1` 是平滑，避免 `E_j = 0` 时除零，也让稀有奖励不会因为 1 个产出就爆表。
- 含义：实际产出高于期望 → 热度 > 1；低于期望 → 热度 < 1。
- 如果 `E_j = 0` 且 `B_j = 0`，热度 = 1；如果 `E_j = 0` 且 `B_j > 0`，热度取 `hMax`。
- 热度只影响**对应奖励**的结算，不跨奖励混用。

### 8.4 超级卡（默认 9 格）

- 默认 **9 格（3×3）**，`config.blackMarket.super.slots = 9`；可调 3–9。
  - **9 格**：默认，图标多、热度标注多；4 种奖励时不可能全不同（9 个图标 / 4 种奖励，鸽笼），通常会有 3–4 连。
  - **3 格**：更极端的高方差预设（可切），37.5% 无对（全单张）/ 56.25% 两连 / 6.25% 三连；适合追求刺激的玩家。
- 每格从并集奖池按 `p_j` **独立抽取（有放回）**，与现有 `drawScratchFace` 的独立抽取语义一致。注意：`p_j` 是浮点概率，**不要直接复用 `drawScratchFace`**（它会把 `weight` clamp 到 ≥1）；用专门的 `drawWeightedFace(prizes, p_j, slots)`，或把 `p_j` 缩放成整数权重（如 ×1e6）再抽。
- 因此每种奖励的出现次数近似二项分布；设全局 `k = super.need`（默认 2），`E[C(n_j,k)] = C(slots,k) × p_j^k`；`k` 的取值影响方差，`E[f_j]` 必须按 `k` 精确算。
- 每格记录 `{ kind, name, heat: h_j }`。
  - 超级卡不携带 `qty/need`：底池 `B_j` 已经是数量，超级卡只负责「哪种奖励超常」。
  - 匹配规则用全局 `k = config.blackMarket.super.need`（默认 2）。混合投入时不同卡种的 `need` 可能不同，统一用一个全局值最干净，也避免同名奖励两套 need。
- 同一个奖励出现多次，每格都显示同一个 `h_j`。
- 某奖励这次实际底池 `B_j=0`（没在投入卡里产出）时，仍可能被抽到；该格显示灰色「底池 0」，结算为 0。这不是漏发，而是这次投入没有该奖励的底池。
- 玩家刮开后（对所有进入超级卡奖池的奖励求和；**没抽到的奖励也按 `f=baseline` 结算**，这是保底）：
  ```
  combos_j = C(n_j, k)                  // n_j = 该奖励在 slots 格里的数量
  expectedCombos_j = C(slots, k) × p_j^k
  f_j = clamp(baseline + (1 - baseline) × (combos_j / max(expectedCombos_j, ε)) ^ fPower, baseline, fMax)
  P_j = B_j × h_j × f_j × payoutRate
  ```
  结果面板要把「未出现的奖励 ×baseline」单独列一行，避免玩家以为漏发。
- **默认（9 格高方差）**：`baseline = 0.05`，`fPower = 2`，`fMax = 10`，`ε = 0.0001`。
- **3 格极端预设**（可选）：`slots=3`，`baseline=0.1`，`fPower=1.5`，`fMax=8`。
- 为什么默认 9 格还能出大方差：
  - 4 种奖励、9 格时，`n_j` 的期望是 2.25；大部分奖励会落在 2–3 连，`f` 约 0.17–1.5；只有少数奖励会吃到 4+ 连，`f` 约 4–10。
  - `baseline=0.05` 让 0–1 连的奖励几乎归零；`fPower=2` 把 4+ 连的奖励拉开；`fMax=10` 保留一个高上限。
  - 结果：**哪个奖励吃到 4+ 连，哪个就爆 2–3× 底池；其他奖励只剩几个百分点**。方差来自这个「选中哪个奖励」的集中度，而不是无对。
  - 9 格比 3 格平滑（同池实测 CV 约 2.0 vs 2.5），但比 `baseline=0.5/fPower=1` 的保底版尖锐得多；具体 CV/分位数由模拟器按实际奖池给出。
- `E[f_j]` 不是 1，也不是固定值：它只由 `slots`、`need`、`p_j`、`baseline`、`fPower`、`fMax` 决定，随 `p_j` 从 ≈`baseline` 到 ≈1.85 变化（默认 9 格/need=2），可以按二项分布精确算：
  ```
  E[f_j] = Σ_{n=0..slots} Binomial(n; slots, p_j) × f(C(n,k))
  ```
  这个值会进入 §8.5 的 `payoutRate` 公式，不能省略。
- `expectedCombos_j` 归一的作用：让不同 `p_j` 的奖励有可比性，不会因为稀有奖励抽到一次就爆炸；`fPower>1` 再把「超常」放大。
- 视觉上 9 个格子（3×3），每格显示 `h_j` 和 `f_j`；命中的奖励类型高亮，结果面板列出最终系数。
- 取整与余料：
  ```
  total_j = B_j × h_j × f_j × payoutRate + dust_j
  pay_j = floor(total_j)
  dust_j = total_j - pay_j      // 0 ≤ dust < 1
  ```
  `dust` 存在 `blackMarket.superDust`，跨次保留，长期期望不被取整系统性压低。
- 产出直接入账：`coin` → `state.coins`；`material` → `state.inventory`。

### 8.5 期望与校准（关键）

设投入 N 张卡，超级卡面与投入卡独立。则：

```
E[Σ P_j] = payoutRate × Σ_j E[B_j × h_j] × E[f_j] × v_j
```

- `E[f_j]`：按上面的二项分布逐奖励精确计算（不是 1；默认 9 格/need=2 时随 `p_j` 在 ≈0.05–1.85 之间变化）。
- `E[B_j × h_j]` **不能**拆成 `E[B_j] × E[h_j]`：`h_j` 是 `B_j` 的函数，两者正相关。对带 `+1` 平滑的线性热度：
  ```
  E[B_j × h_j] ≈ E_j + sensitivity × Var_j / max(E_j + 1, 1)
  ```
- 关键：`E_j` 和 `Var_j` 都是可加的：
  ```
  E_j  = Σ_cards μ_{card,j}
  Var_j = Σ_cards σ²_{card,j}
  ```
  每张卡按自己的 `pool` 快照贡献 μ/σ²，不按 `typeId` 分组；服务端在 `blackSuperStart` 时逐卡累加，因此可以直接算出 `E[B_j×h_j]`，不用按 N 分档查表。
- **统一价值 `v_j`**：超级卡产出是混合物品，不能把 1 个浮木纤维和 1 个鱼币当同价值。默认：
  - `coin` = 1（鱼币）
  - 材料 = 黑市回收价 `coins/per`（如浮木 1/20=0.05、深蓝晶片 1/5=0.2、渊核 0.5、旧日合金 2）
  - 锁钥/特殊物品 = `config.blackMarket.super.valueOverrides`（如潮汐锁钥 3、深渊锁钥 8）
  - **回收表和 overrides 都没有的物品** = `config.blackMarket.super.unknownValue`（默认 0.05）；避免新卡种的新材料让 `v_j` 变成 NaN
  - `v_j` clamp 到 `[0, 1e6]`；`v_j ≤ 0` 的奖励不进入超级卡奖池（见 §8.11.3），避免「有图标但必然 0 收益」
  - 所有 `E_j`、`B_j`、`P_j` 在算期望/方差时都乘 `v_j`；下面公式里的 `Σ` 都是**价值加权**。
- 反推 `payoutRate`：
  ```
  payoutRate = targetEv × Σ_j (E_j × v_j)
             / Σ_j ( E[B_j×h_j] × E[f_j] × v_j )
             × calibrationSafety
  ```
  - `targetEv = 0.975`（目标：投入卡期望价值的 97.5%，落在 95–100% 区间中部）。
  - `evMin = 0.95`，`evMax = 1.00`：这是**长期期望价值**的允许区间，不是单次结果。
  - `calibrationSafety`：解析模式取 `0.98`（补偿 clamp 截断）；模拟模式取 `1.0`（clamp 已在模拟里，最多留 `0.995` 的实现误差）。所以生产的小批量走模拟时，实际长期期望就是 ~97.5%，不是 95.5%。
- **解析/模拟的选择（关键）**：解析式只在 `N ≥ 20` 且每个奖励 `Var_j/E_j² ≤ 0.5`、`clampRisk_j ≤ 0.01` 时使用；否则**强制模拟**（默认 10k 次，`N<5`/`Var/E²>2` 用 50k）。原因：小批量（尤其 1–10 张）的底池分布很偏，线性 `E+Var/(E+1)` 会被热度 clamp 截断，解析费率可能只有真实值的 2/3（1 张）或 0.9（5 张），直接导致实际 EV 掉到 70–90%。**实现不做跨请求校准缓存**：每次开局都重新校准，模拟种子混入本次请求的随机 nonce，避免同一组合反复命中同一段随机流造成长期偏差。
- `calibrationMode`：`'auto'`（默认，按上面的 guard 选）、`'analytic'`（强制解析，仅用于后台对比/校准，线上不推荐）、`'simulate'`（强制模拟）。
- 怎么把期望「控制」在 95–100%：
  1. 先按公式算 `payoutRate`，再算模型期望比：
     ```
     modeledRatio = payoutRate × Σ(E[B×h] × E[f] × v) / Σ(E × v)
     ```
  2. 如果 `modeledRatio < evMin`，说明截断/近似太保守：把 `calibrationSafety` 往上调（≤1.0；后台预览可到 1.05）；如果 `> evMax`，往下调。
  3. 如果 `payoutRate` 被压到 `<0.01` 或模型比率仍无法落进区间，返回 `SUPER_TOO_VOLATILE`，让玩家多投几张或换组合，**不要硬结算**。
  4. 每次超级卡都把 `payoutRate`、`Σ(E×v)`、实付价值存进结果；服务端按 `(poolHash 组合, 张数档位)` 全局滚动统计 `实付价值 / Σ(E×v)`，超出 [0.95, 1.00] 时告警并微调 `targetEv`。这是线上兜底。
- 解析式对 `E[B×h]` 用的是**未截断**值，真实热度被 clamp 到 0.25–4 后通常更小；但小批量/高偏度奖池里线性近似会明显低估，所以 `N<20`、`Var/E² > 0.5` 或 `clampRisk > 0.01` 时必须走模拟（§8.11.7），不能只靠解析式。
- 模拟校准的做法：对这批投入做 10k 次蒙特卡洛（热度和 9 格面都模拟），先模拟出 `R = E[Σ(B×h×f×v)] / Σ(E×v)`，再令 `payoutRate = targetEv / R`；结果只写进本张超级卡，不做跨请求缓存。`calibrationMode='auto'` 已会在小批量/高偏度时自动走这条路，解析式只做大 batch 快速路径。
- `payoutRate` 每个超级卡实例存一份，不写全局配置，避免不同投入混用同一个费率。
- 如果不想维护解析/模拟：把 `sensitivity` 调到 0（热度恒 1），`payoutRate≈0.975 / E[f]`，超级卡退化为「底池 × 匹配倍率 × 0.975 / E[f]」，仍有高方差，但没有热度惊喜。

### 8.6 数值示例（默认潮汐卡，10 张，9 格）

单卡期望（3 槽，need=2）：
- 浮木纤维：`3 × 0.28² × 3 = 0.7056`
- 潮汐树脂：`0.7056`
- 鱼币：`3 × 0.24² × 10 = 1.728`
- 深蓝晶片：`3 × 0.20² × 1 = 0.12`

10 张期望 `E`：木 7.056 / 树脂 7.056 / 鱼币 17.28 / 晶片 1.2。

假设实际底池 `B`：木 9 / 树脂 5 / 鱼币 20 / 晶片 1。

热度（示例用 sensitivity=1；生产默认 1.2，数值会略变；clamp 0.25–4，下面各值都在范围内）：
- 木：`1 + (10/8.056 - 1) = 1.241`
- 树脂：`1 + (6/8.056 - 1) = 0.745`
- 鱼币：`1 + (21/18.28 - 1) = 1.149`
- 晶片：`1 + (2/2.2 - 1) = 0.909`

超级卡 9 格假设为：**鱼币 4 / 浮木 2 / 树脂 2 / 晶片 1**（鱼币 4 连，木/树脂两连，晶片单张）。
- `expectedCombos`：木 `C(9,2)×0.28² = 2.822`；树脂 2.822；鱼币 `36×0.24² = 2.074`；晶片 `36×0.20² = 1.44`。
- 实际组合：鱼币 `C(4,2)=6`；木 `C(2,2)=1`；树脂 `C(2,2)=1`；晶片 0。
- `f = clamp(0.05 + 0.95 × (combos/expectedCombos)^2, 0.05, 10)`：
  - 鱼币：`0.05 + 0.95×(6/2.074)² = 8.00`
  - 木：`0.05 + 0.95×(1/2.822)² = 0.169`
  - 树脂：`0.169`
  - 晶片：`0.05`（单张）
- `E[f]`（9 格二项分布精确值，约）：木 1.761、树脂 1.761、鱼币 1.819、晶片 1.767。
- `E[B×h]`（`E + 1×Var/(E+1)`，约）：木/树脂 10.54、鱼币 29.64、晶片 1.90。
- `payoutRate` 解析值：
  ```
  ΣE = 32.59
  Σ(E[B×h] × E[f]) ≈ 10.54×1.761 + 10.54×1.761 + 29.64×1.819 + 1.90×1.767
                     ≈ 18.55 + 18.55 + 53.89 + 3.36 = 94.35
  payoutRate ≈ 0.975 × 32.59 / 94.35 × 0.98 ≈ 0.330
  ```
  下面用 **0.33** 演示。注意：N=10 在生产会命中 `N<20` 的 guard 走 10k 模拟，实际费率会与解析值略有差异，但更接近 97.5%。

结算：
- 鱼币：`20 × 1.149 × 8.00 × 0.33 = 60.7` → **60**
- 木：`9 × 1.241 × 0.169 × 0.33 = 0.62` → 0（余料）
- 树脂：`5 × 0.745 × 0.169 × 0.33 = 0.21` → 0（余料）
- 晶片：`1 × 0.909 × 0.05 × 0.33 = 0.015` → 0（余料）

**结果：+60 鱼币**。鱼币 4 连是这次的高光局；其他奖励几乎归零。

同样 10 张、9 格，另一种走向（木 3 / 树脂 3 / 鱼币 2 / 晶片 1，没有 4 连）：
- 木/树脂 n3：`f = 1.123`；鱼币 n2：`f = 0.271`；晶片：`f = 0.05`。
- 总产出约 `4.14 + 1.38 + 2.05 + 0.015 ≈ 7.6` 单位，玩家只拿回零头。
- 高光 60 vs 低走 7.6，单次差约 8 倍；长期平均仍 `≈0.975 × ΣE`。这就是 9 格版的「大方差」。

> 如果把 `slots` 调到 3（极端预设 `baseline=0.1/fPower=1.5/fMax=8`），会出现 37.5% 全不同：高光约 77，低走约 1.6，方差更猛；9 格是默认的折中。

> 注意：上例令 `v_j=1`。生产按 §8.5 价值表折算（鱼币 1、浮木 1/20、树脂 1/20、晶片 1/5、渊核 1/2），鱼币占绝对大头，解析出的 `payoutRate` 约 0.30，结果会略有不同。混合投入时，`B/E/Var` 按 `kind:name` 合并、逐卡累加，`p_j` 按每张卡快照的权重加权；公式仍然成立。

### 8.7 状态与动作

```js
state.blackMarket.super = {
  id, at,
  input: [{ typeId, poolHash, count }], // 按 pool 快照分组；typeId 仅展示
  totalCount,
  base: [{ kind, name, qty }],         // 实际底池 B
  expected: [{ kind, name, qty }],     // 期望 E
  heat: { 'kind:name': h },
  face: [{ kind, name, heat }],        // slots 格奖励图标（默认 9）
  pool: [{ kind, name, p, heat }],     // 并集奖池与每格命中概率 p_j（实现使用）
  shape: { slots, need, baseline, fPower, fMax }, // 形状快照
  combos: null,
  payouts: null,
  payoutRate,                          // 本实例的解析/模拟费率
  expectedValue,                       // Σ(E×v)，审计用
  calibration: { mode, maxVarRatio, clampRisk, terms }, // 每个奖励的 E/Var/meanBH/expF/value
  status: 'ready' | 'revealed',
}
```

- 同一时间只能有一张未刮的超级卡；`status = 'ready'` 时不能再开新的。
- `blackSuperStart { cardIds: string[] }`：
  1. 校验最多 200 个 ID，先做 ID 去重（重复 ID 只算一次），逐个要求 `status === 'ready'`、有可用的 `pool` 快照、且该卡至少有一个 `μ>0 且 v>0` 的奖励；任一张不合法则整批拒绝，不消耗任何卡；
  2. 按 `poolHash` 归并计数（仅用于展示和缓存命中），实际计算仍逐卡累加；消耗这些卡；
  3. 用每张卡的 `pool` 结算 `B`、算/读缓存 `μ/σ²`，汇总 `E/Var`；
  4. 排除 `E_j=0` 的奖励；如果全为 0 → `SUPER_EMPTY_BASE`；
  5. 算热度 `h`；
  6. 用 `drawWeightedFace` 按 `p_j` 生成 `slots` 格 `face`（并集奖池，带 `heat`）；
  7. 快照 `shape`，解析计算 `payoutRate`；
  8. 写 `state.blackMarket.super = { status: 'ready', ... }`。
- `blackSuperReveal {}`：
  1. 要求 `super.status === 'ready'`；
  2. 用 `super.shape`、`super.face`、`super.base`、`super.heat`、`super.payoutRate` 算 `combos/f/P`，**不读当前配置**；
  3. 余料累计，产出入账；
  4. `status = 'revealed'`，写入 `lastSuper`（保留最近一次结果），清空 `super`；
  5. 统计：`superConsumed`、`superPayouts`、`superBestCombo`、`superJackpots`。
- 客户端刮开动画只是表现；服务端在 `blackSuperStart` 时已经把 face 定死，`blackSuperReveal` 只做结算。客户端可以提前调用，没有经济优势。
- 断线：`status='ready'` 的超级卡留在快照里，下次登录继续刮；等待期间改配置/关黑市不影响它。
- 重置进度：超级卡和投入卡一起清空。

### 8.8 边界

| 场景 | 处理 |
| --- | --- |
| 不同种类混投 | 允许；按每张卡的 `pool` 快照算 B/E/Var，按 `kind:name` 合并，超级卡奖池取并集 |
| 同名奖励但 kind 不同 | 视为两种奖励（如 `coin:鱼币` 与 `material:鱼币` 不会出现，但规则上分开） |
| 已刮开的卡 | 只取 `status === 'ready'` |
| 投入 0 张 / 超过 200 | clamp；0 张返回 `SUPER_EMPTY` |
| 已有一张未刮超级卡 | `SUPER_PENDING`，先刮完 |
| 卡种被后台删除 | 有 `pool` 快照的旧卡照常；没有快照的旧卡 → `SUPER_UNSUPPORTED_CARD` |
| 后台改已发卡奖池 | 旧卡按发卡时的 `pool` 快照算；新卡用新配置；互不影响 |
| 老卡没有 face | 用 `card.pool` 补抽；没有 pool 再回退当前配置；都没有 → 拒绝 |
| 老卡没有 pool | 迁移时用当时的卡种配置补；补不到 → `SUPER_UNSUPPORTED_CARD` |
| 后台改卡池/权重 | 旧卡按快照；缓存按 `poolHash`；不需要全局重算 |
| 解析出的 `payoutRate` | 它不是概率，`>1` 正常（稀有奖励的 `E[f]` 很小）；只要求有限且 `0.01 ≤ rate ≤ 1e6`，否则 `SUPER_TOO_VOLATILE` |
| 解析 `payoutRate < 0.01` | 返回 `SUPER_TOO_VOLATILE`，提示多投几张；不要用 0.01 硬结算，否则会超发 |
| 热度参数被改 | 解析值自动变化；等待中的卡用 `super.shape` 快照，不受影响 |
| 超级卡全局 `need` | 默认 2、可配 2–3；不随输入卡种变化；底池已经按原 need 结算过 |
| 取整 | `superDust` 跨次保留 |
| 客户端伪造 `cardIds` | 服务端逐张校验 `ready`/归属/快照，不信任客户端数量 |
| 断网/重试 | 动作带 `requestId` 幂等；`blackSuperStart` 不会重复消耗 |
| 未解锁海沟 | `BLACK_LOCKED` |

### 8.9 混合种类规则（已支持）

- 按每张卡的 **`pool` 快照**分组（不是按当前 `typeId`）；每张卡用各自的 `face` 结算、各自的快照算期望。
- 奖励按 `kind:name` 合并：
  ```
  B_j  = Σ_cards B_{card,j}
  E_j  = Σ_cards μ_{card,j}
  Var_j = Σ_cards σ²_{card,j}
  ```
- 超级卡奖池并集：
  ```
  w_{card,j} = p_{card,j} = 该卡快照里奖励 j 的权重 / 该卡「进入超级奖池」的奖励总权重
  w_j = Σ_cards w_{card,j}
  p_j = w_j / Σ w
  ```
  投入张数越多的池子，其奖励越容易出现在超级卡上；这是有意的——你喂得多的池子，热度也更集中。按卡归一后，后台改权重尺度不会改变超级卡概率；`μ=0`/`v=0` 的死奖励不参与分母。
- 超级卡全局 `need` 默认为 2（可配 2–3）：不再区分原卡种每个奖项的 `need`；底池已经把原 need 的效果结算进去了。
- 解析 `payoutRate` 使用合并后的 `E/Var`，任意混合都能把期望锁在 95–100%。
- 某奖励只在少数卡里出现、`p_j` 很小时，`slots` 格里可能抽不到，`f=baseline`；这是正常的，不是 bug。
- 同一卡种在改配置前发出的卡和改配置后发出的卡可以混投：它们各按自己的 pool 快照算，不会互相污染。

### 8.10 可行性结论（写给决策）

**可行**，条件如下：

1. **接受热度×底池的正相关**：不能用 `E[B]×E[h]` 手算期望；用 `E[B h] ≈ E + sensitivity×Var/(E+1)` 按这批投入逐卡累加的 μ/σ² 解析，或用 10k 模拟直接校准 `payoutRate`。
2. **校准必须分模式**：解析式只在 `N≥20 且 Var/E²≤0.5` 时使用；小批量/高偏度强制 10k 模拟。模拟模式 `calibrationSafety=1.0`（解析模式 0.98），再用上线前复核和线上滚动 `实付/ΣE` 审计，把长期期望控制在 **95–100%**。
3. **默认 9 格（3×3）**：`baseline=0.05`、`fPower=2`、`fMax=10`、热度 clamp 0.25–4。4 种奖励时 9 个图标通常出现 3–4 连；吃到 4+ 连的奖励爆 2–3× 底池，其余奖励只剩几个百分点。方差来自「选中哪个奖励」的集中度，不是无对。
4. **想要更刺激**：把 `slots` 调到 3，配 `baseline=0.1`、`fPower=1.5`、`fMax=8`；4 种奖励时 37.5% 无对 / 56.25% 两连 / 6.25% 三连，单次离散度更猛。
5. **兼容任意刮刮乐配置**：每张卡带 `pool` 快照，μ/σ² 按快照算并缓存，超级卡只认快照不认当前配置；`need>slots`、全 0 权重、同名奖励、卡种删除等退化情况都有明确行为（§8.11）。
6. **不想维护解析/模拟**：改成「独立倍率制」——投入卡正常结算并入账，超级卡只提供独立倍率；期望容易算，但投入张数对产出不再线性补偿，需要另设规则。

### 8.11 兼容所有可配置的刮刮乐

后台可以任意增删卡种、改 `slots`、改奖池、改权重、改 `need`、同名奖励不同数量/需求，甚至设出 `need > slots` 的永远不中奖条目。超级卡不能假设「4 种奖励 / 3 槽 / need=2」，必须做到：

#### 8.11.1 发卡时快照奖池

`makeScratchCard` 除了 `face`，再存一份 **pool 快照**：

```js
card.pool = {
  slots: type.slots,
  prizes: type.prizes.map(p => ({
    kind: p.kind, name: p.name, qty: p.qty, weight: p.weight, need: p.need,
  })),
}
```
- 快照存 `normalizeScratchPrize` 之后的**有效值**（`weight≥1`、`need` 2..10、`qty≥1`），`slots` 用与 `drawScratchFace` 相同的 clamp（2..10）；与 `drawScratchFace`、`scratchSettlement` 实际使用的值完全一致，不要存后台原始输入。

- 超级卡只认 `card.pool` 和 `card.face`，**不读当前 `config.scratchTypes`**。
- 快照膨胀：v1 直接把 `pool` 挂在每张卡上（一个卡池只有几个奖项，几十字节）；如果同种卡堆到几百张，可改为 `state.scratchPools[poolHash]` 去重、卡上只存 `poolHash`，语义不变。两种存法都按 `poolHash` 命中 μ/σ² 缓存。
- 后台之后改奖池/删卡种，已发出的卡仍按发卡时的池子算 μ/σ²、算 p_j。
- 旧卡没有 `pool`：迁移时用当时的 `config.scratchTypes[typeId]` 补一份；补不到（卡种已删）就标记为 `unsupported`，超级卡拒绝这张卡（`SUPER_UNSUPPORTED_CARD`），而不是拿别的卡池硬算。
- 迁移补快照时做一次**卡面校正**：
  - 如果 `card.face.length` 与补出的 `slots` 不同，以 `face.length` 为准写回 `pool.slots`（实际抽了几格是已知的）；
  - 如果卡面里出现补出奖池中没有的奖励，按卡面携带的 `qty`/`need` 补进快照（`weight` 记 1），并标记 `poolSource:'reconstructed'`；
  - 这样至少保证每个实际出现过的奖励都有 `μ>0`，不会被误判为 0 底池。
- `poolSource` 只用于审计：`exact`（新卡）、`migrated`（同配置补全）、`reconstructed`（卡面有未知奖励）、`missing`（卡种已删，不可投入）。`reconstructed` 的 E 是近似值，允许投入，但后台统计里单独标记；要绝对精确就让玩家先把旧卡正常刮完。
- 正常刮开仍用 `card.face`；没有 face 的老卡用 `card.pool` 补抽（没有 pool 再回退当前配置，保持现有兼容逻辑）。

#### 8.11.2 μ/σ² 按快照懒计算并缓存

单张卡的 `μ/σ²` 只由 `pool` 决定，可以**精确算**，不需要枚举所有卡面：

- 先按原结算键 `kind:name:qty:need` 分组（与 `scratchSettlement` 一致），组 `g` 的单格命中概率：
  ```
  p_g = Σ(组内条目 weight) / Σ(全部 weight)
  N_g ~ Binomial(pool.slots, p_g)
  ```
- 单组期望与方差（`need > slots` 时组合数为 0，自动 μ=0）：
  ```
  E_g = q_g × C(slots, need_g) × p_g^need_g
  E2_g = q_g² × Σ_{n=0..slots} Binom(n; slots, p_g) × C(n, need_g)²
  Var_g = E2_g − E_g²
  ```
  二项分布只需 O(slots)，10 格以内是常数级。
- 按 `kind:name` 合并时，不同结算组可能来自同一张卡的不同格子，不能直接相加方差：
  ```
  M_g = C(slots, need_g) × p_g^need_g          // 期望组合数（不含 qty）
  μ_j  = Σ_g q_g × M_g
  Var_j = Σ_g Var_g + 2 × Σ_{g<h} Cov(g,h)
  Cov(g,h) = q_g q_h × [ Σ_{a,b} Multinomial(a,b; slots, p_g, p_h) × C(a, need_g) × C(b, need_h) − M_g M_h ]
  // Multinomial 的剩余槽位是其他奖励，概率 1−p_g−p_h
  ```
  双重求和是 O(slots²)，且只有同名不同 `qty/need` 的组才需要算；普通卡池只有一组同名，协方差为 0。
- 组数 ≤32 时全精确；超过 32 组（后台极端堆料）改用固定种子的 1 万次模拟并缓存，同时在后台标黄提示「组合过多，使用模拟校准」。
- 按 `poolHash` 缓存（LRU，几十条足够）；缓存键包含 `slots` 和全部 `prizes` 字段的规范化 JSON 哈希。
- 投入卡可以是不同快照的混合；`E_j = Σ_cards μ_{card,j}`、`Var_j = Σ_cards σ²_{card,j}`，不按 `typeId` 分组。
- `need > slots` 的条目 μ=0；它不会贡献底池，也会被排除出超级卡奖池（见下）。
- 这样新增卡种、改奖池都不需要改黑市代码或做每卡种校准；精确公式也避免了「模拟噪声导致同一批卡两次开局费率不同」。

#### 8.11.3 超级卡奖池按「可支付奖励」的并集

- 只把 `μ_j > 0` 且 `v_j > 0` 的奖励放进超级卡奖池；`μ_j = 0`（永远不中奖）和 `v_j = 0`（无价值）的条目不出现，避免出现「有图标但永远无产出 / 收益为 0」的死格。
- **不按本次实际底池 `B_j` 过滤奖池**：奖池只由投入卡的快照决定，否则 `E[f_j]` 会依赖 `B`，解析校准公式失效，等于把底池方差也平滑掉。某奖励这次 `B_j=0` 但仍可能出现在超级卡上，结算自然是 0；UI 用灰色「底池 0 / ×0」标示，不隐藏。
- `v_j` 的解析顺序：`coin` → 1；`valueOverrides['kind:name']` → `valueOverrides[name]` → 配置值（支持按 kind 精确覆盖）；`materials` 回收表 → `coins/per`；否则 `unknownValue`。任何情况下都不会出现 `undefined/NaN`，新卡种的新材料也能直接工作。
- 权重（先按卡归一，再跨卡相加；分母只算进入超级奖池的奖励）：
  ```
  w_{card,j} = 该卡快照里奖励 j 的权重 / 该卡「进入超级奖池」的奖励总权重
  w_j = Σ_cards w_{card,j}
  p_j = w_j / Σ w
  ```
- 如果所有奖励都不可支付（`μ_j=0` 或 `v_j=0`），返回 `SUPER_EMPTY_BASE`，不消耗卡。
- **任一张投入卡的可支付奖励集合为空**（整张卡都是 `need>slots` 或 `v=0`）→ 整批拒绝 `SUPER_EMPTY_BASE`，不消耗任何卡；不要静默跳过，避免玩家以为卡被吞。这样每张被接受的卡都有正的归一化分母，`p_j` 的 `1/N` 才成立。
- 同名但 `kind` 不同的奖励分开（`kind:name`）；同名同 kind、不同 qty/need 的条目在超级卡里合并为一个奖励：μ 相加，Var 相加并计入组间协方差，权重相加；超级卡不携带 qty/need，所以不会冲突。
- 超级卡全局 `need` 默认为 2（可配 2–3）与输入卡的 `need` 无关；输入卡的底池已经按它自己的 need 结算过。

#### 8.11.4 超级卡形状快照

`blackSuperStart` 时把当时的形状存进实例：

```js
super.shape = { slots, need, baseline, fPower, fMax }
super.payoutRate = ...       // 按这批投入算好
super.targetEv / expectedValue
```

- `blackSuperReveal` 只用 `super.face`、`super.base`、`super.heat`、`super.shape`、`super.payoutRate`；后台在等待期间改任何配置都不影响这张已生成的卡。
- 新开的超级卡才读新配置。
- `enabled=false` 时：禁止新开/买卖，但允许 `blackSuperReveal` 结算已有的 `ready` 卡，避免卡死在快照里。

#### 8.11.5 退化与极端配置

| 配置 | 行为 |
| --- | --- |
| 1 个奖励且必中 | `p=1`，9 格全是它；`f=1`；产出 = 底池 × 热度 × `payoutRate`；无面方差，只剩输入/热度方差 |
| `need > slots` | 该奖励 μ=0，不进超级卡奖池；若全部如此 → `SUPER_EMPTY_BASE` |
| 2 槽 / 10 槽卡 | 正常按快照算 μ/σ²；超级卡固定 9 格，不受影响 |
| 奖池 20+ 种奖励 | `p_j` 可能很小；`E[f_j]` 按二项分布算；9 格里可能抽不到，`f=baseline`，正常 |
| 同名不同 qty/need | 普通刮开仍按原 `scratchGroupKey` 分组；超级卡按 `kind:name` 合并，μ 相加、Var 计入协方差、权重相加 |
| 奖励不在回收表/overrides | 用 `unknownValue`（默认 0.05）计价；不会 NaN，也不会把新卡种卡死 |
| 奖励价值为 0 | 不进入超级卡奖池；若全部为 0 → `SUPER_EMPTY_BASE` |
| 权重全 0 / 非法 / 过大 | `normalizeScratchPrize` clamp 到 `1..1e9`（全 0 归一后等价均匀）；总权重不会溢出，`p_j` 有限 |
| qty 非法 / 过大 | clamp 到 `1..1e9`；单奖励底池 `B_j×v_j` 再按 `1e12` 保护；超出拒绝整批 |
| `pool.prizes` 为空/非法 | 视为 `unsupported`，超级卡拒绝该卡；不拿默认奖池硬算 |
| 新卡 `face` 与 `pool` 奖励集合不一致 | 视为损坏/篡改 → `SUPER_UNSUPPORTED_CARD`；旧卡按 §8.11.1 的 `reconstructed` 规则处理 |
| 卡种被删除 | 有 `pool` 快照的旧卡照常；没有快照的旧卡 → `SUPER_UNSUPPORTED_CARD` |
| 老卡没有 face | 用 `pool` 补抽；没有 pool 再回退当前配置；都没有 → 拒绝 |
| 等待期间改 super 配置 | `super.shape` 已存，结算不受影响 |
| 等待期间关黑市 | 已有 `ready` 卡仍可 `blackSuperReveal` |
| targetEv 超出 0.95–1 | `normalizeConfig` clamp；模型比率压不进区间 → `SUPER_TOO_VOLATILE` |

#### 8.11.6 后台的兼容性提示

- 编辑/删除卡种时提示：「已有 N 张未刮卡使用旧奖池；超级卡按发卡快照结算。」
- 黑市后台加一个「兼容性检查」：
  - 对每个卡种模拟 μ/σ²，检查至少有一个 `μ>0` 的奖励；
  - 计算超级卡在该池下的 `E[f]`、解析 `payoutRate`、模型期望比；
  - 标出 `need > slots`、全 0 权重、极端 qty、`v=0`/未知价值、`clampRisk` 过高、可能 `SUPER_EMPTY_BASE` 的配置。
- 这样后台可以放心加新卡种、改奖池，不需要重跑每卡种的黑市校准表。

#### 8.11.7 极端分布下的期望保险

解析式在两种情况下会失准：热度被 clamp 截断，或单个奖励的 `Var/E²` 极大（少量超大奖品主导底池）。为了保证「任意配置都落在 95–100%」：

- **先算一个截断风险指标**：
  ```
  upper_j = E_j + (heatMax - 1) × (E_j + 1) / sensitivity
  lower_j = E_j - (1 - heatMin) × (E_j + 1) / sensitivity
  clampRisk_j ≈ P(B_j > upper_j) + P(B_j < lower_j)
  ```
  用 `B_j` 的分布近似估；只要 `N < 20`、任一奖励 `clampRisk_j > 0.01`、或 `max_j(Var_j / max(E_j, ε)²) > 0.5`，就**强制走模拟校准**（`simSamples` 次），不用解析式。
- 为什么是 `N<20`：小批量的底池分布最偏，实测 1 张时解析费率只有真实值的 ~0.68、2 张 ~0.82、5 张 ~0.90；20 张以上、`Var/E²≤0.5` 时线性近似与真实 `E[B×h]` 的误差 <0.5%。
- 模拟样本：默认 `simSamples=10000`；`N<5` 或 `Var/E²>2` 时用 50000，降低重尾分布的均值噪声。校准缓存键必须包含 `poolHash 组合 + 张数 + shape 哈希（含 targetEv/calibrationSafety）+ 价值表版本`；后台改任何相关参数后，旧缓存自动失效。
- 模拟实现：先按 §8.11.2 预计算**单卡每种奖励的结算分布**（不是每次重画 slots 个格子），再按张数抽样求和；否则 200 张 × 10 格 × 10k 次会达到 2000 万次抽格，单次请求会明显卡顿。只校准均值时可以按各奖励的边际分布独立抽样；要输出总产出的分布/分位数时，必须按同一张卡的多奖励联合分布抽样（或直接重画格子），否则会低估相关性。模拟用独立的确定性 PRNG（种子 = `poolHash 组合 + 张数 + shape + 本次请求 nonce`），**不要消耗 cryptoRandom 的 face 流**；nonce 让同一组合的多次开局不会重复同一段随机序列。
- **模拟校准也压不进区间**（分母 ≤0、`modeledRatio < evMin` 或 `> evMax`，或 `payoutRate < 0.01`）→ 返回 `SUPER_TOO_VOLATILE`，提示「这批卡的奖励太偏，请多投几张或换组合」，一张卡都不消耗。
- **单奖励底池上限**：`B_j × v_j` clamp 到 `1e12`；超过的批次直接拒绝（`SUPER_TOO_VOLATILE`），避免 Infinity/精度丢失。
- **线上滚动审计按 `(poolHash 组合, 张数档位)` 分组**：`实付价值 / Σ(E×v)` 连续 N 次超出 `[0.95, 1.00]` 时，按方向微调该组合的 `calibrationSafety`（每次 1%，限制在 `0.95–1.0`），并告警；这是对解析/模拟误差的最终兜底。
- 这样极端配置只会被「拒绝开局」，不会悄悄超发或吞掉玩家投入。

## 11. 服务端动作

| 动作 | 参数 | 说明 |
| --- | --- | --- |
| `blackAcknowledge` | `{}` | 首次点击品牌锁进入时置 `introSeen=true`；幂等，不校验解锁 |
| `blackSellFish` | `{ fishIds: string[] }` | 最多 100 个 ID；逐条校验资格/配额 |
| `blackSellMaterial` | `{ name, units }` | `units` 是想要的渔币组数 |
| `blackRefreshOrder` | `{}` | 扣 25 渔币，重掷订单 |
| `blackSuperStart` | `{ cardIds: string[] }` | 1–200 张未刮开卡（可混合）；消耗并生成超级卡 |
| `blackSuperReveal` | `{}` | 结算当前 `super`，入账，写 `lastSuper` |
| `blackBuy` | `{ itemId }` | 商店购买/服务 |
| `setTheme`（现有动作加强校验） | `{ theme }` | `void` 未购买时无效 |

- `blackAcknowledge` 是唯一**不要求已解锁**的黑市动作：它只写一个 UI 标记，不解锁任何东西；未解锁时调用也返回成功。这样解锁瞬间的扫光不会因为时序问题卡住，也不需要为「看没看过入口」单独开接口。
- 其余黑市动作统一先过 `assertBlackUnlocked(state, config)`：`enabled && unlockedDepths.includes(unlockDepth)`，否则 `BLACK_LOCKED`。

通用规则：

- 参数先 `String/int` 收敛、clamp，再进领域函数。
- 不信任客户端的价格、倍数、价值；客户端只传 ID/数量/类型。
- 领域函数返回同一个 `state` 引用表示不生效；需要明确原因的用 `HttpError`：
  - `BLACK_QUOTA`、`BLACK_INELIGIBLE`、`BLACK_FUNDS`、`BLACK_LIMIT`
  - `SUPER_EMPTY`、`SUPER_PENDING`、`SUPER_NOT_READY`、`SUPER_TOO_VOLATILE`
  - `BLACK_LOCKED`
- 幂等：沿用 `/api/action` 的 `requestId` 日志；`blackSuperStart` 重试不会重复扣卡。
- 并发：沿用 `withPlayerLock`。
- 随机源：订单生成、超级卡面都用 `cryptoRandom`；领域函数带 `random` 参数，测试可注入。
- 一次 `blackSuperStart` 最多 200 张，避免单请求过大。

## 12. FX 与仓库完整性（关键）

### 12.1 用户要求

> 黑市交易的鱼不会像商会一样影响股票（和放在仓库不卖出一样）。

这里的「股票」即游戏里的**深海 FX** 行情。

FX 的现有规则：

- **上钩**：词条被抽离市场 → 记 `+1` 份/词条（正流入，供给减少）。
- **商会卖出**：词条回到市场 → 记 `−1` 份/词条（负流入，供给增加）。
- 鱼躺在仓库：不产生任何流水，等价于「永久抽离」。

黑市卖鱼：鱼被消耗，但不调用 `fxExchangeFlow`，所以**只有上钩时的正流入，没有卖出的负流入**。这和「把鱼永远放在仓库」完全一致，满足用户要求。

### 12.2 为什么必须有每日配额

仓库容量是有限的（默认 1000，天赋扩到 10000），所以「永久抽离」的总量有上限；一旦仓库满，钓鱼停止，FX 供给不会被无限抽干。

黑市如果不限购：

- 玩家可以钓一条卖一条，仓库永远不满；
- 每条鱼都永久抽离词条，且不回补；
- 长期净流入持续为正，FX 价格被持续推高；
- 黑市变成了「绕过仓库容量的无限仓库 + 额外给渔币」。

这会直接破坏 FX 的供需模型，也和现有「满仓必须停钓」的设计冲突——仓库容量本来就是给「永久抽离」设的上限。

因此：

- **每日收购配额是硬性设计**，默认 40 条/天；
- 配额用完后，鱼只能去商会（回补 FX）或继续躺在仓库；
- 配额可通过渔币扩到 100 条/天，仍是有界；
- 后台可以把 `dailyQuota` 调大，但不建议关掉。

### 12.3 验收测试

```
1. 记录 state.fx.today
2. 钓一条符合条件的鱼（正流入）
3. 黑市卖出
4. 断言 state.fx.today 与卖出前完全一致（没有新的负流入）
5. 断言 blackMarket.coins 增加、鱼 status = 'black'
6. 对照：同一条鱼走商会 → fx.today 出现负流入
```

## 13. 边界与反滥用清单

### 13.1 未刮开卡面保密（黑市前提）

超级卡的底池 `B` 来自投入卡的实际结算，所以「未刮开卡面」在黑市里变成了可获利信息。如果客户端能拿到 `card.face`，玩家可以只挑高产出卡投入，把长期期望从 97.5% 拉到远超目标；这不是数值问题，是信息泄露。

现状：`makeScratchCard` 把 `face` 存进玩家快照，sync 整包下发；`ScratchCard` 组件直接读 `card.face`。

要求：

- **服务端持久化保留 `face`，HTTP 响应剥离**：`extractPlayerState` 仍用于落库（必须保留 `face`，否则重启后卡面丢失）；在把状态发给客户端之前（`sync`/`me`/action 响应）调用 `redactScratchFaces(state)`，对 `status === 'ready'` 的卡只保留 `{ id, typeId, status, createdAt, poolHash, slots }`（`slots` 用于卡种被删时仍能渲染占位），不下发 `face`/`payout`/奖励名。
- 具体落点：`server/routes/game.js` 的 3 处 `me: extractPlayerState(...)`（sync、fishing tick、action）和 `server/services/reset.js` 的 reset 响应，统一改为 `redactScratchFaces(extractPlayerState(...))`；`players.js` 内部的落库调用保持原样。
- 客户端未刮开时按 `card.slots ?? type.slots` 渲染 `?` 占位；涂层全覆盖，玩家看不到占位内容。卡种被删时 `type` 会回退到第一个卡种，**必须优先用 `card.slots`**，否则格数会错。
- **刮开体验会变**：现在是「涂层下面已经画好卡面，刮开即见」；保密后涂层下面是 `?`，刮到阈值 → 调 `revealScratch` → 服务端返回 `face` → 客户端替换 `?` 并做一次 180ms 翻牌/淡入。刮的手感不变，但「边刮边看见图标」会变成「刮完才亮牌」。这是保密的必要代价，不要试图在客户端缓存 face 绕过。
- 刮开进度到阈值时调用现有 `revealScratch` 动作；服务端返回该卡的 `face`/`payout`，客户端再用返回值渲染。正常刮刮乐流程不变，只是「翻牌」从本地读取改成动作返回。
- `economySignature` 目前只含 `scratchCards.length`，不泄露卡面；不要为了签名把 `face` 放进下发字段。若后续需要检测单卡变化，用服务端的 `faceHash`，不下发。
- 黑市选卡 UI 只显示卡种/数量/池子标签，不显示任何卡面信息；`blackSuperStart` 只接受 `cardIds`。
- 旧客户端/旧接口如果仍下发 `face`，黑市必须 `enabled=false` 或拒绝 `blackSuperStart`，直到保密层上线。

验收：

- 未刮开卡的 sync JSON 中搜不到 `face`、`payout` 或奖励名；
- 客户端无法通过任何接口在 `blackSuperStart` 前拿到 `face`；
- 同一批 `cardIds` 的底池只由服务端自己的 `face` 计算，客户端参数不影响 B/E/Var。

| 场景 | 处理 |
| --- | --- |
| 客户端已知未刮卡面 | 未刮卡的 `face` 不下发；黑市只按服务端 face 算底池（§13.1） |
| 客户端伪造鱼价/倍数 | 服务端只认公式与配置 |

| 卖已兑换/已黑市出售的鱼 | `status !== 'fresh'` → `BLACK_INELIGIBLE` |
| 鱼含禁用词条 | 拒绝，返回原因 |
| 配额已满还卖 | 单条 `BLACK_QUOTA`；批量卖到配额为止 |
| 刷新后已售鱼 | 不回滚、不返还配额 |
| 超级卡混投不同种类 | 允许；按 `kind:name` 合并底池，奖池取并集，全局 `need` 默认 2 |

| 一次回收 1e9 材料 | 单次上限 1000 组 |
| 渔币负数 | 扣减前校验，状态归一化清零 |
| 订单词条被后台删除 | `applyConfig` 清空订单，下次 sync 重生成 |

| 重置进度 | 渔币/购买/订单/超级卡清空；限定主题回退；`introSeen=false`（重新解锁海沟后扫光再现） |
| 客户端时间改快 | 日切/倒计时以服务端 `serverTime` 为准 |
| 客户端直接调 `setTheme('void')` | 服务端校验购买记录 |
| 未解锁时点击品牌锁 | 不切换、不报错；`blackAcknowledge` 可以调用但不产生解锁 |
| 黑市模式刷新页面 | 回到鱼市默认页；`introSeen` 已落库，扫光不再出现 |
| 黑市模式中途被禁用 | `useEffect` 回退到 `lastFishTab` + toast；动作返回 `BLACK_LOCKED` |
| 黑市模式下点管理后台 | 入口不渲染；先回鱼市 |
| 移动端品牌锁误触 | 品牌锁与 `mobile-close` 分开事件，`stopPropagation`；切换后关抽屉 |
| 限定钓竿重复购买 | 检查 `purchases` + 现有竿 baseId |
| 维修满耐久钓竿 | 不扣渔币，返回无效 |
| 超级卡取整偏差 | `superDust` 跨次保留余料 |
| 超级卡断线 | `status='ready'` 留在快照，下次继续刮 |

  - 发卡后删除卡种：有 `pool` 的卡照常；无 `pool` 的旧卡返回 `SUPER_UNSUPPORTED_CARD`，且不消耗其他卡；

## 附录 A：为什么线性热度会爆，而且和投入张数有关

> 本附录用不含 `+1` 平滑的理论版 `h = B/E` 说明机制；实际实现是 `h = 1 + s×((B+1)/(E+1)-1)`，精确式对应 `E + s×Var/(E+1)`，数值略低，但「随投入张数下降」的结论不变。

设投入 N 张卡，某奖励的单卡产出为随机变量 X，均值 μ、方差 σ²。底池 `B = ΣX`，期望 `E = Nμ`，方差 `Nσ²`。混合投入时 `E = Σ_cards μ_card`、`Var = Σ_cards σ²_card`，公式不变。

线性热度：
```
h = 1 + (B - E) / E = B / E
```
则：
```
E[B × h] = E[B²] / E = (Var(B) + E²) / E = E + Var(B)/E
         = Nμ + Nσ² / (Nμ) = Nμ + σ²/μ
```
所以：
```
E[B×h] / E[B] = 1 + σ² / (N μ²)
```

**关键：这个比值随 N 增大而下降。** 默认潮汐卡：

| N | 木/树脂 | 鱼币 | 晶片 | 合计（按期望加权） |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 6.63 | 8.57 | 11.67 | **7.8×** |
| 10 | 1.563 | 1.756 | 2.067 | **1.68×** |
| 100 | 1.056 | 1.076 | 1.107 | **1.07×** |

- 单卡投入时，热度会把幸运底池放大得非常猛；100 张投入时，热度几乎回到 1。
- 所以 `payoutRate` 不能是一个固定的 0.95；必须用 `E/Var` 解析式按这批投入重算，否则小批量会超发、大批量会欠发。
- clamp `heatMax=4` 会把上限压住，但 `B` 大时 `B×4` 仍然线性增长；最终还是要用解析式按这批投入的 `E/Var` 重算 `payoutRate`，并用模拟器复核 clamp 带来的偏差。

## 附录 B：独立倍率制（备选）

如果不想处理上面的相关性：

- 投入卡正常结算并直接入账（或只把底池入账）；
- 超级卡只提供**独立的倍率**，例如 9 格匹配给 `×0.5 / ×1 / ×2 / ×5 / ×10`；
- 最终产出 = 底池 × 独立倍率 × payoutRate；
- 因为倍率与底池独立，`E = E[底池] × E[倍率] × payoutRate`，可以手算；
- 代价：投入卡的「实际奖励」只影响底池，不影响热度；「根据实际结算奖励算热度」的语义变弱。

**推荐先做本稿的底池+热度制；如果模拟后发现分布太极端，再退回独立倍率制。**
